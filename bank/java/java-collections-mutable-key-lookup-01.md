## Ask

An `Order` class has `equals` and `hashCode` generated by the IDE from all of its fields. The code
puts an order into a `HashSet`, then sets `customerId` on that same object. After that,
`set.contains(order)` returns false — but a loop over the set still prints it. What is going on?

## Tests

Whether the candidate can connect a hash-based lookup to the promise the stored object has to keep
for the lookup to work at all.

## Ideal minimal answer

The set filed the order by a value derived from its fields, and changing one after it went in
means the lookup now goes somewhere that no longer matches, while walking the set derives
nothing and still finds it. Says a stored key must not change, or must take its identity from
fields that do not.

## Listen for

- The set goes to a position derived from the object's current hash, and after the field changed it
  is filed somewhere that no longer matches
- Walking the set derives nothing, which is why the object is still visibly in there
- Removing it fails for the same reason, so the entry is stranded for the life of the set
- States the rule: anything used as a key must not change while it is stored, or must not take its
  identity from fields that change

## Expected knowledge

- Two objects that are equal must return the same hash, and hash-based collections rely on it
- The difference between a linear scan and a direct lookup

## Strong signals

- Suggests the identity come from something stable, such as the order number, rather than every field
- Points out the same defect hits map keys, and that the stranded entry is also a slow leak
- Asks whether the object needed to be mutable in the first place

## Weak signals

- Recites "you must always override both" with no account of why this lookup fails
- Blames the set implementation, or asks for a method that rebuilds it
- Puts the object in again and moves on

## Answer bands

### weak

- Says the set is broken, or that this is expected because objects change.
- Cannot explain why the loop still shows the object.
- Suggests re-adding it with no account of what is now in the set.

### junior

- Says the value used to place the object changed after it went in.
- Connects the failed lookup to the two methods being derived from every field.
- Suggests keeping the key fields fixed while the object is stored.

### mid

- Walks through placement on insert and lookup, and shows where the two diverge.
- Notes that removal also fails, so the entry can never be got rid of.
- Proposes deriving the two methods from a stable business key and says what that decides about
  when two orders count as the same one.

## Follow-ups

- Same object, but the field is set before it ever goes into the set. Any problem?
  probes: whether they see that only a change while stored breaks it
- Someone rewrites the two methods over just the order number. What did that just decide for the
  rest of the codebase?
  probes: choosing a stable key, and that it redefines what "the same order" means
- You inherit two hundred classes written this way. How would you work out which ones can actually
  bite?
  probes: which types are used as keys, and which of their fields change after construction

## Notes

The card is about the mechanism, not about the two method names. A candidate who says "equals and
hashCode" in the first breath and then cannot say why iteration still finds the object has not
answered it.
